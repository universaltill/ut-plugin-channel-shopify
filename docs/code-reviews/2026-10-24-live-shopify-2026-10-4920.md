# Review: three queries that failed on real Shopify 2026-10 (ut-docs#4920)

Reviewer: Opus 5.5 (independent worktree review of the WIP snapshot; the author's model was Sonnet 5.5). Verdict after fixes: safe to merge.

## What shipped (v0.2.2)

- `stock.set`: every quantity now carries `changeFromQuantity` (the cloud's
  `expect`, or an explicit `null` for no compare). `ignoreCompareQuantity` is gone
  (the field does not exist in 2026-10).
- `inventoryActivate` carries `@idempotent(key:)` with the op id.
- No order query selects `customer`; the contact answer takes its name from the
  shipping address. Orders carry no `customer` ref (the contract makes it optional).
- `internal/fakeshop/realapi.go` makes the fake refuse what the real API refused,
  with its own test; README rows marked verified; version 0.2.2.

## Evidence beyond the unit tests

The plugin's own query texts were dumped (throwaway test, not committed) and sent
to the owner's development store with the app's granted scopes: 17 of 22 passed
before the change; the 3 failures are exactly these. Real mutations on test data:
stock set (null, matching, stale), price update and read-back, activate with
`@idempotent`, fulfil with tracking, partial refund, cancel + job poll.
Nothing from the store is committed.

## Findings

The reviewer ran gofmt, vet (native and wasip1), `go test ./...`, `validate.sh`, shellcheck and the version-bump test (all green), and re-verified the test-first claim by reverting the four production files: about 25 order, contact and stock tests went red with the real errors, green again on restore.

| # | Severity | Finding | Outcome |
|---|---|---|---|
| 1 | major | One op id was the `@idempotent` key of two different mutations (`inventoryActivate`, then the set); an answer of the wrong shape would have been acked as a successful set | Fixed: the activation uses `<op>:activate`; a missing set answer is a retryable `bad_answer`, never an ack. Test `TestStockSetActivationAndSetCarryTheirOwnKeys` |
| 2 | major | Orders carry no customer ref, so ut-cloud's `has_customer` is false and my. hides "Show contact"; `customer_country` is lost | Accepted for this PR (far better than ACCESS_DENIED on every order) and carded: ut-docs#4923 (ut-cloud + ut-my-shop) |
| 3 | minor | A redelivery after an activation compares where the first delivery did not: the same key with other input | Fixed: a set of a level that was not held uses `<op>:new`. Verified live: same key, different input is `IDEMPOTENCY_KEY_PARAMETER_MISMATCH`; the redelivery now gets `CHANGE_FROM_QUANTITY_STALE`. Test `TestStockSetRedeliveryAfterActivationIsJudgedOnItsCompareNotItsKey`; the fake models per-operation key fingerprints (`keyMismatch`) |
| 4 | minor | `realapi.go` caught only `customer {` | Fixed: `\bcustomer\s*[{(]`; new `TestNoQuerySelectsTheCustomerObject` over every query text |
| 5 | nit | stale comment, dead `if res.Name == ""`, test struct, README wording ("failing looks like" column, "were run") | Fixed |

## Verified beyond the tests (2026-10-24, owner's development store)

All 22 query texts of the final code are accepted by the real Admin API 2026-10 (variables shaped as the plugin sends them; mutations on fake ids or on test data). Real writes: stock set (null, matching, stale), activate with its own key then set with `:new` then a compare redelivery (stale), price update with read-back and restore, fulfil with tracking, partial refund, cancel with job poll. Same key across two different mutations was accepted by Shopify (so finding 1 was a defence, not an observed failure).

## Deferred

- ut-docs#4923: contact button and customer country for customer-less orders.
- Webhooks, the cloud host's own outbox/sweep and a multi-location item were not exercised (needs the shop session).

## Verdict

Safe to merge.
